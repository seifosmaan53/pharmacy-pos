- Added a 10-test **Playwright** suite (8 originally, 2 added in review) against a throwaway seeded SQLite DB, plus

## Browser test suite

Files: `playwright.config.ts`, `e2e/{db,fixtures,setup-db,global-teardown}.ts`,
`e2e/pharmacy.spec.ts`.

**Isolation.**
- The server runs as `next start` (a production build) on port 3100. Its
  `DATABASE_URL` is a fixed absolute path to `prisma/e2e.db`.
- Before the server starts, `e2e/setup-db.ts` deletes that file, runs
  `prisma migrate deploy` (the real migrations) and seeds data.
- Global teardown deletes the file afterwards. Set `E2E_KEEP_DB=1` to keep it.
- `assertE2EDatabase` refuses any other URL. The path is not read from the
  environment, so the suite cannot reach `dev.db` or any other database.
- `prisma/*.db` is already git-ignored.

**Data.**
- Synthetic users: manager `9001` and pharmacist `9002`, with test-only passwords.
- One fictional supplier.
- Fictional products: "Zentorix 10mg" (two batches, expiring in 60 and 300
  days), "Quellamine Syrup" and "Brivolax 5mg".
- The test-only `SESSION_SECRET` lives in the config.

**Mocks.** None. The app calls no external services (no outbound HTTP clients
in `app/`, `lib/` or `components/`), so nothing needed to be mocked. The PDF
receipt is generated in-process by pdf-lib.

| # | Test | UI action | Persistence check |
|---|---|---|---|
| 1 | Unauthenticated `/pos` | visit | redirected to `/login` |
| 2 | Wrong password | submit login | error shown, still on `/login` |
| 3 | Sign out revokes session | sign in, sign out, revisit `/dashboard` | redirected to `/login`; Prisma: `tokenVersion` incremented by 1 |
| 4 | Pharmacist sale with FEFO | sell 15 units, pay 100 | reload shows 50 → 35 available. Prisma: `Sale` by serial with total 6000¢, paid 10000¢, balance, `soldBy` = pharmacist, one item ×15; soon batch 10 → 0, late batch 40 → 35. PDF receipt returns 200 (`application/pdf`) with a session and **401** without one |
| 5 | Oversell blocked (client) | try to add available + 1 units | "Only N pcs … available" shown. Prisma: sale count and stock unchanged. This stops at the client-side cart check; the server is not called |
| 6 | Oversell blocked (server) | cart filled to the available quantity, then one unit is taken in the DB before checkout | server error "Not enough stock …" shown; reload shows the reduced level. Prisma: sale count unchanged, stock reduced only by the simulated unit (restored afterwards) |
| 7 | Manager receives stock | modal form: 60 units, 9.00 / 13.75, expiry +400 days | after reload the row shows `60 / 60`. Prisma: batch in cents (900/1375), drug price updated to 1375, supplier, `createdBy` = manager, expiry date, availability +60 |
| 8 | Manager deletes batch | Delete + accept confirm | row gone after reload. Prisma: batch count 0 |
| 9 | **Denied permission** (pages) | pharmacist opens `/staff` and `/suppliers`, views `/stock` | redirected to `/dashboard?denied=1` with the "restricted to managers" notice; no Staff link and no Delete buttons. Prisma: user and stock counts unchanged |
| 10 | **Denied permission** (Server Action) | the request a manager's Delete sends is captured and aborted, then replayed with a pharmacist session, then with the manager session as a control | Prisma: batch survives the pharmacist replay, is deleted by the manager replay |

Tests 5–6 and 9–10 cover the same rules on the client and on the server. Tests 6
and 10 were added in review: mutation testing showed that removing
`requireManager()` from `deleteStock`, or the `INSUFFICIENT_STOCK` check in
`allocateFEFO`, left the original 8 tests green. See
`drafts/review/REVIEW-deps-and-e2e.md`.

**Does the suite catch real bugs?** As a one-off check, I made
`decrementStockFEFO` allocate latest-expiry-first, rebuilt and reran test 4. It
failed (`Expected: 0, Received: 10` on the soon batch). Then I reverted the
change. That change was never committed.

## CI

New job `e2e` (ubuntu-latest, Node 20, 20-minute timeout):
1. `npm ci`
2. `prisma generate`
3. `npx playwright install --with-deps chromium`
4. `npm run build`
5. `npm run test:e2e`
6. Upload `playwright-report/` and `test-results/` on failure

The existing `build` job (install, generate, migrate, lint, typecheck, unit
tests, build) is byte-for-byte unchanged.

**Unverified:** GitHub Actions has not run this workflow. This session has no
remote, and the Playwright CDN is blocked here, so `playwright install --with-deps
chromium` was never executed. The steps were reproduced locally in a fresh clone
under Node 20.20.0 / npm 10.8.2, but using the preinstalled browser.
